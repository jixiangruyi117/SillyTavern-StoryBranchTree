# 剧情分支树（SillyTavern Story Branch Tree）

在单人角色聊天中创建和管理多条剧情路线：可选择全部路线保存在同一条聊天中，或使用酒馆原生分支、在界面按故事归组。从任意楼层分叉、在分支里继续分支，也能切回其他路线接着聊。

> [!IMPORTANT]
> 这是用户维护的 SillyTavern 第三方界面扩展，不属于 SillyTavern 官方项目，也不修改酒馆核心文件。

## 核心功能

- **从任意楼层分叉**：同一个分叉点可创建多条路线，子路线也能继续分叉。
- **重说回复独立成线**：从当前显示的 AI 回复建立路线；历史楼层可切换回复，之后仍能回到对应路线。
- **切换路线并继续游玩**：确认后切换到主线或任意分支，原路线后续内容会保留。
- **可视化剧情树**：全屏查看路线、分叉点和终点；支持详细/简略视图、缩放、平移、定位、整理和拖动布局。
- **备注和摘要**：为路线、分叉点添加名称、摘要或备注，查看末楼内容。
- **两种保存方式**：单聊天模式将所有路线放在当前聊天中；原生分支模式使用独立聊天文件，聊天管理入口按故事归为一项。
- **本地运行**：分支树本身不调用模型、不连接外部服务；仅支持单人角色聊天，不支持群聊。

## 安装

在 SillyTavern 的 **扩展 → 安装扩展** 中粘贴仓库地址：

```text
https://github.com/jixiangruyi117/SillyTavern-StoryBranchTree
```

安装后刷新页面。点击聊天输入框左侧的魔法棒，在菜单中选择 **剧情分支树** 打开全屏树状图。在任意消息旁点击 **分支** 并确认，即可创建路线。树中点击路线名可查看详情并确认切换；删除路线也需要确认。

画布支持滚轮缩放和拖动平移；触屏设备可双指捏合缩放。点击 **定位当前** 将正在聊天的路线移到画布中央，点击 **整理布局** 重新排列节点。路线末尾楼层可查看正文，触屏长按或鼠标拖动可调整位置。

### 故事模式与聊天列表

第一次打开尚未建立剧情树的聊天时，选择 **单聊天模式** 或 **原生分支模式**。模式按故事固定，子路线沿用相同模式；已有单聊天存档自动沿用原机制，不迁移或混用。当前不提供模式互转。

原生模式调用酒馆原生分支和打开聊天流程；每份聊天只保存自己的正文、插件数据和轻量路线描述，不把其他路线正文/记忆快照放入元数据。保存当前路线仍是酒馆的全量保存，公共前文仍会在分支文件中重复；这不是后端增量存储。

点击树图的 **故事**，或在扩展启用时打开酒馆聊天管理入口，同一原生故事显示为一项，内部可展开路线。**查看原始记录** 可随时进入酒馆原始聊天管理；停用扩展后原生文件仍可独立打开。其他扩展自行绘制的列表不自动归组。分组目录和布局备注使用现有扩展设置保存，路线身份保存在各聊天文件中。外部改名、导入记录或目录丢失时点击 **重建分组**；只有显式查找旧分支、重建分组和整故事导出/删除会读取聊天列表的元数据，普通列表不下载各路线正文。身份冲突的复制文件保留为可见原始记录。

**首页最近聊天归组（0.1.75，含 TT 酒馆）**：同一故事的已知原生路线收起为一项，打开后通过分支树切换。点击 **显示各路线记录** 可展开；停用扩展后恢复原列表。只使用已有分组目录，不额外读取聊天文件；未整理的旧分支、身份不明确的记录及群聊保持原样。首页预览、置顶、改名和删除仍对应当前显示的那一条路线，删除整个故事请使用树中的故事列表。标记的路线数只统计本次最近列表中出现的记录，不是故事总路线数。

**整理安装前的旧原生分支（0.1.72）**：打开同一故事的任意一条现存聊天，包括子分支或孙分支 → 打开剧情分支树 → **查找整个故事**（也可从「故事」列表进入）→ 核对并勾选记录 → **整理所选记录** → 确认。无需先找到主线，也无需模型 API。

- 根据酒馆保存的来源聊天名向上寻找，并反向寻找同来源的其他分支；只处理当前角色。有明确原生分叉记录且楼层内容吻合时，恢复分叉位置。原生检查点也可能有关联，会单独标注且默认不勾选。
- 主线已删除时，仍可通过共同来源归组现存子分支，树图标注来源缺失；不会新建或伪造主线。分叉位置不明时标为「分叉位置未知」，可切换、续聊，但不能从未知节点直接开新分支，应在聊天中选择实际楼层。
- 预览和取消不会添加归组标记。确认后保留原文件名、正文、重说、插件记忆及未知数据，只补故事和消息/回复身份信息；不把多个文件合并成一份，也不恢复以前未记录的记忆版本。新纳入的当前聊天在预览前已有的未保存内容会随确认保存。
- 只按明确来源归组，不根据相似文件名或正文猜关系。来源丢失、文件改名后关联失效可能找不全；单聊天模式、循环关联、重复路线身份及不同已归组故事之间的冲突不会自动合并，目前不提供任意旧记录的手动认领。
- 仅在主动查找时读取当前角色的元数据列表，再以最多 4 条并发检查相关聊天；普通列表不执行旧分支扫描。相关聊天很多、插件元数据很大时查找会耗时，可取消。确认后逐文件保存并核对，暂不支持跨文件原子提交；失败会保留已完成项和全部文件，可按原选择继续或重新查找。整理期间请勿在其他设备编辑同批聊天。

TT 的聊天列表未返回来源信息时，0.1.75 会通过 TT 公开的轻量元数据接口补齐当前角色的聊天关联，每批最多 4 条，不为此下载所有正文。旧版 TT 缺少该接口时会明确提示；不会跳过来源冲突检查。已在电脑隔离酒馆按 TT 的接口形状复现并验证一楼旧分支查找、整理，以及首页收起/展开、置顶刷新和停用还原；另通过桌面浏览器模拟窄屏检查布局，未在实体手机上测试。

原生模式末楼普通重说沿用酒馆行为，不为每个候选回复新建文件；在尚未续写的末楼换回复仍是修改当前路线。历史楼层的其他回复先只读预览，不改变当前路线后续；确认 **新建路线并继续** 才创建指定回复的原生聊天。已有对应续写显示 **继续：路线名**，同一回复可有多个续写供选择，不自动选取其中一条。关联使用稳定消息与回复版本身份。原生模式已在 SillyTavern 1.19.0 的真实接口验证；旧版本无法选择指定重说时会停止该操作，不通过修改源聊天绕过。

原生路线详情可删除该路线及子路线，其他文件保留；故事列表的 **删除故事** 会另行确认全部路线。若新分支文件已创建但后续步骤失败，保留文件并显示其名称，可从原始记录恢复。

**导出当前路线** 下载普通 JSONL，保留正文及插件数据，移除本扩展的故事关联和父聊天链接，作为独立聊天导入。**导出故事** 下载 `.story.json`，包含全部路线和布局/节点备注；通过故事列表的 **导入故事** 恢复，导入会生成新的故事/路线身份和文件名，不覆盖已有聊天。不要把整故事文件作为普通 JSONL 导入。

## 路线数据与记忆隔离

以下共享前文和快照机制适用于 **单聊天模式**。原生模式每条路线使用真实独立聊天及其原有插件数据；正常切换走酒馆聊天加载事件，通用适配器仍可参与切换准备、历史分叉和恢复。原生分叉会继承当前聊天元数据，**不会自动把已经总结到后面的聊天级记忆倒退到历史分叉点**；只有插件自身可回溯或已接入接口时，才能按其能力恢复。未知插件内部缓存或数据库不会被自动修改。

分支图保存在当前聊天的 `chat_metadata.story_branch_tree` 中。酒馆聊天数组始终显示当前选中的一条线性路线；切换时，扩展从共享前文和路线后缀重建聊天数组。路线使用稳定消息标识定位分叉点；原生重说回复也分别记录标识和已选择的回复。

分支树会按路线保存原生 `is_hidden` / `is_system` 状态，以及**已注册适配器明确声明**的消息字段和聊天元数据字段。分叉时继承当前已有的数据；之后不同路线独立更新。声明的数据随聊天导出和导入。正文仍使用共享前文与分支后缀保存，因此长期、多路线聊天会增加单个聊天文件的体积。

插件作者可阅读[通用路线记忆接口教程](docs/MEMORY_ADAPTER_API.md)，注册适配器、声明自己拥有的字段，并在路线切换时恢复自己的缓存。0.1.71 内置原生模式的记忆增强 2.2.19 桥接，0.1.73 恢复此前单聊天模式的记忆增强专用适配；其他插件继续按原有逻辑运行，其聊天级缓存、外部数据库或向量索引不会自动按路线隔离。没有逐楼记录的历史摘要也无法凭空还原到分叉点。

通用接口包括路线查询、路线消息读取、字段快照、切换钩子和后台任务凭证。没有分支时，不会自动启动记忆适配器任务或模型请求；未使用接口的普通聊天流程不受适配代码影响。字段或恢复职责由多个适配器重复声明时，注册会被拒绝。

### 单聊天模式与记忆增强（0.1.73 恢复）

适用于标准目录 `st-memory-enhancement` 下的 **2.2.19**，无需修改记忆增强源码。选择单聊天模式后自动接入；原生模式继续使用下节的桥接，两者按当前聊天模式交接，不同时接管表格。

- **在当前楼层开分支**：继承当前表格；之后各条路线分别填表、手动改表，切回来恢复各自保存的结果。
- **回到旧楼层开分支**：依据保留的楼层表格记录恢复，剔除新路线没有用到的后期单元格，不把原路线后面的表格内容带过去。对应单元格历史已丢失时会停止恢复并提示，不能凭空补回。
- **从历史楼层的另一版重说继续**：保存过表格结果的回复恢复自己的记录；没有记录的新回复会尝试解析它正文里的有效 `tableEdit` 填表指令。没有记录、也没有有效填表指令时，不保证还原那版回复应有的记忆，需检查并在记忆增强中补填。
- **切换、刷新和导入**：路线表格随同一份聊天存档保存。0.1.73 已用真实插件的解析、保存和加载逻辑，验证当前/历史分叉、其他重说、嵌套分支及手改；六条路线往返切换、整页刷新、JSONL 再导入后，均恢复各自预期的单元格值。测试使用合成聊天，不调用模型；此前 0.1.64/0.1.65 的真实填表测试属于历史验证，本轮未重新调用模型。
- **范围限制**：单聊天适配恢复已记录的表格内容，**不提供原生桥接那种逐回复的表名、列结构和删表回溯保证**。全局模板、设置和外部向量库不随楼层倒退；没有保存过的旧手改结果无法补回。其他三个记忆插件在单聊天模式没有专用适配，不能套用下节原生模式的通过结论。

适配会跟踪已核对的填表/重建入口，在表格操作未结束时阻止路线切换，并在恢复时刷新插件缓存。外部脚本绕过这些入口直接改数据、生成中换聊天、全部双步填表配置及多记忆插件同时启用不在本轮验证范围；仍请等生成、填表等任务全部结束后，再分叉或切换。

字段范围：柏宝书检查了地点、主角状态、变量、物品、计划、场景和 NPC，并通过实际界面分别修改两条路线的物品数量；Horae 检查了地点、物品、NPC、服装、事件和关系，并检查分叉后各线新增的手动地点记忆互不覆盖；记忆增强及数据库检查了同一张测试表的逐楼记录和各路线分别修改的单元格。没有覆盖 Horae 的 RPG、自定义表格、全部压缩摘要配置，也没有覆盖任意表结构变更、外部向量库或四家同时启用的组合。

真实 API 补测（非流式、各家分别启用）：柏宝书生成两种回复并实际摘录，Horae 解析模型输出的记忆标签，记忆增强执行模型输出的单步 `tableEdit`。三家从历史另一个重说分叉后续写、再切回源线续写，实际发给模型的提示词只含各自路线的测试记忆，没有另一路线或被截去的后期物品。柏宝书另用真实 L1 总结、Horae 用真实自动压缩摘要测试覆盖范围中间的历史分叉，本例实际注入均排除了分叉点之后的剧情；这不改变整段导入旧总结和没有历史版本的手工数据限制。

数据库另测了两份原生聊天的真实填表（源线手动触发，子线在正常发送后自动填表），并绑定专用测试世界书。隐藏旧正文后，分别生成的实际请求包含各自表格，不含另一路线的钥匙；切换后世界书会异步刷新，本例等待其结束后两向读取也正确。填表需要足够的输出额度：初次沿用测试正文的 500-token 上限导致结果截断，调至 3000 后重测成功。此结果不覆盖数据库历史重说分叉，也不覆盖记忆增强的独立双步填表；向量嵌入/召回仍未测试。

**所有插件都要注意：回到旧楼层不等于回到那一天的全部设置和手动修改。** 后来直接改在早期摘要上的内容、全局/角色设置，以及没有逐楼版本的共享记忆，仍可能保留现在的值。柏宝书的“导入旧总结”是整段历史，实测回到其覆盖范围中间分叉时，仍会带入总结中后面的剧情；从其他聊天携带的整段记忆和向量包也不承诺自动切分。使用这些功能时，请在新分支检查并用记忆插件自身的编辑功能修正；分支树无法凭空还原没有保存过的历史版本。

### 路线编号、重说和聊天状态

路线编号用于树图展示，实际关系由稳定路线 ID 保存。普通分支按父路线、分叉楼层和同点的路线序号排列；重说路线会标明回复楼层。同一分叉点创建的多个子路线分别编号，嵌套分支按各自父路线继续排列。

普通 **分支** 从当前消息的活动回复之后继续；从历史 AI 回复创建重说路线时，该回复成为新路线的起始楼层。历史回复箭头由分支树接管：切换到尚未续写的回复后，发送下一条消息并确认，才会为它创建路线；切回已有回复时会恢复该回复原来的后续路线。

路线切换会恢复消息本身的数据、路线记忆快照以及各路线的 `chat_metadata.variables`，再重建消息界面并发送酒馆的“聊天已加载”事件。重说回复中按 `variables[swipe_id]` 保存的状态随对应回复保留；未保存为逐楼或逐回复状态的数据无法还原到过去。

## 当前限制

- 仅支持单人角色聊天，不支持群聊和临时助手聊天。
- 单聊天模式的分支共用同一个聊天 ID；未接入路线 API 的扩展若按聊天 ID 或外部存储维护状态，其数据仍可能被不同路线共用。原生模式使用独立聊天 ID，也不保证所有第三方插件均能正确回溯历史。
- 单聊天模式删除或修改共享前文可能影响其他路线；请使用分支树管理路线，不要直接删除共享楼层。原生模式的分支文件互相独立。
- 旧摘要若没有逐楼或可回溯数据，无法自动重建分叉前的准确记忆。

### 记忆适配性能与适用边界（0.1.74）

- 单聊天模式去掉普通消息同步时额外的整段回复采集；保留记忆插件保存、填表完成时的采集，以及分叉/切换前的采集。历史表格筛选合并为一次单元格池遍历，完整性检查仍保留。
- 原生模式保存表格时直接判断存储模式，不再为此生成整段聊天的消息 ID 列表；最近一次表结构按当前内容核对，避免每次遍历并序列化所有旧版本。官方批量存表入口在聊天真正保存前统一采集一次，出错仍释放批次。表格通知不再顺带保存无关树图布局/扩展设置；历史恢复也不再为校验少量引用而构造整个单元格池的 ID 集合。
- 对照为恢复后的 0.1.73 工作区与 0.1.74，1000/4000 楼、41/161 条路线、3/6 张表，原生另有 40/160 个表结构版本；五轮独立进程交替执行，完整保存数据摘要一致。单聊天测试「一次插件保存 + 三次消息同步」，耗时中位数分别 **203→168 ms、1788→1357 ms**，分配量采样 **120→93 MiB、830→619 MiB**；大档深拷贝调用 **60006→24006**。原生测试十次批量存表，适配耗时分别 **2.70→0.64 ms、19.07→1.20 ms**，大档回复采集 **70→10 次**，实际聊天保存仍为十次。
- 这些是桌面 Node 合成负载下的本插件处理成本，不含模型、网络、酒馆渲染及记忆插件自身的全部处理。原生测试有路线数量参数，但测量主体是当前聊天的批量存表，不代表遍历 161 个聊天文件。大档单聊天进程峰值工作集约 **1194→1027 MiB**（包含数据准备）；原生约 **220→219 MiB**，不能把分配量下降当作整页常驻内存同比下降。
- **不能保证任意规模都不卡。** 单聊天仍需维护当前投影并全量保存含全部路线的文件，长正文、表格历史和很多分支仍会变重。原生通常更适合长聊天/云酒馆：普通存表不读取其他分支文件，但每份文件仍重复公共前文，酒馆仍全量保存当前文件；首次查找/重建分组、导出整个故事和绘制大量树节点仍有相应成本。用于回溯的旧表结构/删表记录不自动丢弃，公开 API 的防御性复制和恢复前后的必要保存也保留。其他记忆插件自身的摘要、向量、数据库或界面开销未改动。

复测适配基准：在改动前将运行代码复制到独立临时目录，设置 `MEMORY_ADAPTER_BASELINE_DIR` 为该目录，再运行 `npm run bench:adapters`。基准只使用合成数据和核心调用替身，无网络或模型请求；两条链路另做真实桌面酒馆的保存、历史/重说分叉和刷新重开回归。生成或记忆任务未结束时切换仍不在保证范围。

内存对照基准运行 `npm run bench:memory`，默认与优化前提交 `ba06b33b10458a73ff40f40e1f7f04fc0591c362` 比较，需本地 Git 中存在该提交。基准使用两档合成数据，每档独立进程交替测量五次，核对路线结果和序列化存档一致；输出分配量采样、进程峰值工作集、操作结束堆增量与耗时。分配量不等于峰值或浏览器常驻内存，进程峰值包含数据准备；该结果不能替代真实酒馆及设备测量。
